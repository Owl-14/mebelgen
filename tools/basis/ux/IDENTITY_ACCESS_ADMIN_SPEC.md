# Identity & Admin — продуктовый план

Статус: `HYPOTHESIS / LOCAL VERTICAL SLICE`

> Важно: описанный ниже интерфейс support-сессии с причиной и TTL заменён
> решением UX-032. Актуальный основной путь — `Открыть компанию` без формы,
> с сохранением личности Akeda, заметным контекстом и автоматическим аудитом.
> Демо-компания и tenant-миграция описаны в
> [DEMO_COMPANY_AND_ADMIN_VIEW_SPEC.md](DEMO_COMPANY_AND_ADMIN_VIEW_SPEC.md).

## Зачем этот блок

Akeda должен обслуживать несколько мебельных компаний в одном продукте, не
смешивая их сотрудников, изделия, AI-историю и производственные артефакты.
Platform-команда Akeda должна создавать организацию и первого владельца, видеть
состояние клиента и безопасно открывать диагностический контекст по обращению.

Это самостоятельный продуктовый контур, а не модальное окно поверх Studio.

## Пользователи и основные работы

### Platform owner Akeda

- создаёт компанию после продажи;
- указывает первого владельца и получает созданные системой логин/пароль;
- видит статус компании, сотрудников, последнюю активность и технические лимиты;
- при обращении открывает ограниченную support-сессию с причиной;
- блокирует компанию или пользователя, отзывает доступ;
- видит общий platform-audit.

### Владелец / администратор компании

- входит по выданным Akeda данным;
- владелец самостоятельно добавляет обычных сотрудников и получает стартовый
  пароль, показанный один раз;
- владелец назначает роли в пределах допустимого, блокирует сотрудника и
  отзывает его сессии;
- администратор видит состав команды, но не меняет сотрудников;
- видит аудит своей компании;
- предоставляет и отзывает доступ поддержки.

### Сотрудник

- входит под собственной учёткой;
- видит только компании и действия, к которым привязан;
- получает Studio с функциями своей роли;
- не видит platform-инструменты и чужие компании.

## Карта продукта

```text
/login
  └─ вход / принятие приглашения / восстановление

/admin
  ├─ Компании             platform only
  │   ├─ реестр
  │   ├─ создание компании + первого owner
  │   └─ карточка: сотрудники / доступ / активность / support
  ├─ Доступы              platform only
  │   └─ активные support-сессии и приглашения
  ├─ Аудит                platform или organization scope
  └─ Система              platform only, позже

/workspace
  ├─ Каталог компании
  └─ Studio конкретного project_id
```

## Первый локальный вертикальный срез

В первой итерации реально работают:

- вход и выход platform admin;
- server-side session + CSRF;
- создание компании;
- создание первого active owner с одноразово показанным стартовым паролем;
- просмотр карточки компании;
- централизованное создание дополнительных сотрудников platform owner;
- блокировка/возобновление membership и смена допустимой роли;
- append-only журнал административных событий;
- создание и завершение read-only support-сессии с причиной и TTL;
- постоянная полоса support-контекста.

В первой итерации честно заблокированы:

- просмотр проектов, AI-чатов и каталогов компании;
- переход в рабочий Studio от имени tenant;
- email-доставка приглашений;
- password reset и MFA/passkeys;
- billing/quota UI.

Причина блокировки Studio: текущие `paramspecs/`, версии, preview, build history и
runtime-состояние общие. Их сначала нужно перенести на tenant-aware repository.

## Экранный и визуальный контракт

### Характер

Не «SaaS dashboard с карточками», а спокойная операторская консоль дорогого
инженерного продукта. Она родственна Studio по типографике, линиям, акценту и
плотности, но ясно показывает более высокий уровень доступа.

- нейтральные белые/серые плоскости и тонкие разделители;
- один синий акцент выбора/действия;
- компактные строки, табличные числа, минимум декоративных контейнеров;
- радиусы 4–6 px, без градиентов, glassmorphism и тяжёлых теней;
- локальные бренд-ассеты и единая система inline SVG-иконок;
- platform-контекст подписан постоянно, а не спрятан в аватаре;
- signature element — техническая boundary-strip: обычная синяя для platform,
  янтарная и постоянно видимая для support-сессии.

### Реестр компаний

- слева узкая навигация уровня платформы;
- сверху строка контекста, поиск и `Создать компанию`;
- центр — таблица, а не KPI-карточки: компания, статус, владелец, сотрудники,
  активность, доступ поддержки;
- выбор строки открывает правый inspector без потери позиции в реестре;
- пустое состояние объясняет одно действие: создать первого клиента.

### Карточка компании

- идентичность и статус;
- сотрудники в плотной таблице;
- отдельные действия `Пригласить`, `Изменить роль`, `Заблокировать`;
- read-only support action с обязательной причиной;
- проекты/AI-история показываются как следующий этап, а не фальшивые данные.

### Создание компании

Один короткий поток:

1. название компании;
2. имя и email первого владельца;
3. проверка результата;
4. компания создаётся транзакционно;
5. оператор получает одноразовую activation link и видит её только один раз.

Platform admin не читает существующий пароль клиента. Система сама генерирует
шестизначный буквенно-цифровой пароль, показывает его один раз и хранит только
Argon2id hash; кнопка перевыпуска немедленно отзывает старый пароль и сессии.

## Данные

Минимальные сущности:

- `users` — глобальная личность и credential status;
- `organizations` — компания и lifecycle status;
- `memberships` — пользователь + компания + роль + status;
- `sessions` — opaque hashed sessions;
- `invitations` — hashed single-use activation tokens;
- `support_sessions` — platform actor + company + reason + scope + expiry;
- `audit_events` — append-only административные события.

Следующая миграция добавляет `organization_id` в `projects`,
`project_revisions`, `ai_operations`, `artifacts` и `build_jobs`.

## Порядок реализации

### Phase 1 — Identity foundation

- SQLite schema и миграции;
- password hashing, login/logout, sessions, CSRF, throttling;
- bootstrap первого platform admin только локально;
- permissions и audit helpers.

### Phase 2 — Administration

- реестр и карточка компаний;
- owner/staff invitations;
- membership role/status;
- read-only support-session shell.

### Phase 3 — Tenant-aware project repository

- стабильный `project_id` вместо имени файла как identity;
- organization-scoped ParamSpec/revisions/previews/artifacts;
- устранение process-global `st.spec` / `st.spec_path`;
- persisted AI operations и project activity;
- мигратор существующих файлов в одну выбранную organization.

### Phase 4 — Protected Studio

- permission middleware для каждого Studio endpoint;
- tenant-aware catalog, open/save/version/export/build;
- support read-only enforcement and banner inside Studio;
- two-tenant BOLA/IDOR regression matrix.

### Phase 5 — Production identity

- transactional email provider;
- password reset;
- MFA/passkeys для platform/owner/admin;
- per-tenant quotas and billing controls;
- retention/offboarding/export policy;
- monitoring and security alerts.

## Review текущего среза

При совместном review отвечаем только на четыре вопроса:

1. Понятно ли, что это платформа Akeda, а не кабинет отдельной компании?
2. Понятно ли, как создать компанию и передать доступ владельцу?
3. Достаточно ли информации в реестре и карточке без перегруза?
4. Выглядит ли support-доступ осознанным и безопасным, а не скрытым входом?
