# Runbook изменений мебельного движка

Статус: **обязательный**. Этот документ читают полностью до любого изменения,
которое способно повлиять на путь «ТЗ → ParamSpec → 3D → присадки →
производственный результат». Требование закреплено в `tools/basis/AGENTS.md`.

Цель runbook — сохранить главный инженерный контракт: нейросеть понимает запрос
и выбирает семантическое изменение, а детерминированный Python-движок проверяет
данные, рассчитывает детали, координаты и присадки. Валидный JSON от LLM ещё не
означает валидную или производимую мебель.

## 1. Карта потока данных

```text
текст/фото ТЗ
  → intent.classify
  → vision_facts (только факты с изображения, если оно есть)
  → create_paramspec | edit_operations | part_edit | answer_query | diagnosis
  → Pydantic-контракт ParamSpec / typed EditOperation
  → атомарное применение к копии текущей ревизии
  → production_gate
      Pydantic → JSON Schema → generator → consistency → geometry
      → CFRN encoding/holes parity → drilling geometry
      → completeness/materials
  → только при зелёном gate: новая ревизия, 3D, BOM, чертёж/экспорт
```

Ни prompt, ни провайдер LLM, ни UI не являются источником истины. Источник
истины по входному контракту — Pydantic-модели в `src/paramspec.py` и
`src/edit_operations.py`; по производимости — `src/production_gate.py`; по
геометрии — генераторы; по присадкам — hardware-конвейер.

## 2. Контракты AI-узлов нельзя смешивать

| Узел | Вход | Допустимый выход | Что запрещено |
|---|---|---|---|
| `vision_facts` | изображения ТЗ | ограниченное текстовое описание видимых фактов | строить координаты, менять объект, додумывать скрытые размеры |
| `create_paramspec` | пустой объект/черновик + ТЗ | **полный** ParamSpec | typed patch вместо изделия; сохранение до полного gate |
| `edit_operations` | текущий ParamSpec + команда | список типизированных операций с preconditions | свободная замена всего ParamSpec; несвязанные изменения |
| `part_edit` | объект и выбранная деталь | только разрешённые операции детали | менять материалы, габариты или соседние детали без прямого запроса |
| `answer_query` | ParamSpec/вычисленный контекст + вопрос | только ответ | любая мутация |
| `diagnosis` | ошибки проверок и контекст | объяснение/план исправления | скрытая мутация или обход quality gate |

Режим определяет детерминированный router в `src/prompt_registry.py`, а не поле,
которое вернула модель. Например, `created=true` от LLM не даёт права заменить
весь объект в режиме редактирования. В режиме создания полный ParamSpec должен
приниматься и без необязательного флага `created`, если route —
`create_paramspec` и весь production gate зелёный.

Операции нормализуются только когда исправление однозначно выводится из уже
переданных полей. Разрешено, например, восстановить target
`dimensions.<dimension>` у `SetDimension`. Нельзя придумывать отсутствующий id,
размер, материал, артикул, координату или смысл команды. Неоднозначный ответ
отклоняется с машинным кодом ошибки; автоматический repair может быть только
ограниченным по числу попыток и снова проходит ту же строгую валидацию.

## 3. Что за что отвечает

| Область | Основные файлы | Ответственность |
|---|---|---|
| ParamSpec | `src/paramspec.py`, `schema/paramspec.schema.json`, `rules/paramspec.md` | типизированная входная модель и JSON Schema |
| Маршрутизация и prompts | `src/prompt_registry.py`, `prompts/spec_chat/*.txt` | выбор узла, его capability schema, версии промптов и ограниченный контекст |
| Провайдеры и чат | `src/spec_chat.py`, `src/providers.py` | вызов vision/LLM, разбор ответа, разделение create/edit, usage и trace |
| Операции | `src/edit_operations.py` | Pydantic-модели операций, preconditions, copy-on-write и атомарность |
| Семантическая геометрия правок | `src/edit_engine.py`, `src/overrides.py` | перевод разрешённых команд детали в детерминированные overrides |
| Оркестрация | `src/studio_graph.py`, `src/orchestrator.py` | граф шагов, bounded repair, защита ревизий и сохранение |
| Генераторы | `src/generators/registry.py`, `src/generators/*.py` | панели, размеры, placement и конструкция каждого архетипа |
| Присадки/фурнитура | `src/hardware.py`, `src/hardware_geometry.py`, `src/fasteners3d.py` | система 32, отверстия, крепёж и его 3D-представление |
| Материалы | `src/materials.py`, `src/materials_policy.py`, `materials/` | реальные материалы/артикулы, резолвинг и политика полноты |
| Quality gates | `src/production_gate.py`, `src/*_check.py`, `src/validate.py` | единое решение, можно ли принять ревизию и производить изделие |
| CFRN/B3D | `src/cfrn.py`, `src/b3d_*.py`, `src/build_b3d.py` | кодирование и проверка производственных файлов |
| Studio/API | `src/studio.py`, `rules/studio.md` | каталог, API, сохранение ревизий, UX ошибок и запуск pipeline |
| 3D-viewer | `src/webviewer.py` | отображение уже рассчитанной модели; не источник геометрии |
| Наблюдаемость | `src/telemetry.py` | privacy-safe spans, prompt/model/version, usage, error codes, trace id |
| Регрессии | `tests/`, `tests/regression.py`, `qa/trace_eval/`, `goldens/` | доказательство совместимости, производимости и offline replay AI-выходов |

Перед правкой открой также профильный документ из `rules/`, на который ссылается
`tools/basis/AGENTS.md`.

## 4. Что можно менять

Меняй только то, что относится к явному запросу и подтверждено контрактом:

1. Параметры ParamSpec, которые пользователь прямо назвал, через подходящую
   типизированную операцию.
2. Правила генератора конкретного архетипа, когда задача действительно меняет
   конструкцию, и только вместе с тестами остальных архетипов.
3. Prompt конкретного узла — вместе с его версией, capability schema и тестом
   результата, а не только сравнением текста.
4. Новый purpose присадки — одновременно во всех реестрах, 3D и проверках.
5. Studio/UI — сохраняя API-контракты, права доступа, текущий каталог и parity с
   viewer.
6. Материал — только через реальную запись/кандидата базы; generic-значение
   остаётся «не выбрано», а не превращается в выдуманный декор.

Любая принятая AI-правка создаётся на копии. Текущая ревизия изменяется или
сохраняется только после успешной валидации и production gate.

## 5. Что не трогать без прямого запроса

- Несвязанные поля ParamSpec, даже если модель предлагает «улучшение».
- `schemaVersion`, catalog identity, ownership, revision/history, audit и права.
- Числовые координаты деталей, placement и отверстий: их считает генератор.
- `overrides`: это узкий аварийный/детальный механизм, не универсальный способ
  исправлять генератор.
- Конструктивные дефолты, толщины, зазоры, система 32 и purpose присадок.
- Артикулы и названия материалов, которых нет в базе.
- Другие архетипы, производственные экспортеры и goldens «заодно».
- Секреты, токены, содержимое пользовательских ТЗ/изображений и полный ParamSpec
  в логах или trace.
- Платные Basis/cloud-вызовы и production deploy без явного разрешения.

Если прямой запрос конфликтует с производственной безопасностью, не ослабляй
gate. Верни понятную ошибку, code, trace id и объясни, какое решение требуется.

## 6. Как добавлять обновления

### Новое/изменённое поле ParamSpec

1. Изменить Pydantic-модель в `src/paramspec.py`.
2. Определить: обязательность, default, диапазон, применимые архетипы и поведение
   старых объектов. Не использовать неявную массовую миграцию.
3. Перегенерировать/сверить `schema/paramspec.schema.json` штатным способом.
4. Обновить генераторы и все потребители поля.
5. При редактировании добавить typed operation либо явно доказать, что существующей
   достаточно.
6. Добавить unit-тесты валидного, граничного и запрещённого значения.
7. Добавить/обновить fixture ParamSpec и regression/golden только после ручной
   проверки осознанной разницы.
8. Обновить `rules/paramspec.md` и этот runbook, если изменился общий контракт.

Сейчас каноническая версия — `paramspec-v1`. Название ветки, класса или UI
«v2» не делает данные ParamSpec v2. Новая версия схемы требует отдельного
дизайна миграции, dual-read/явного converter, обратимости, метрик ошибок и
отдельного согласования. Старые каталоговые объекты не переписывать массово при
открытии.

Версионная граница v1 описана в `rules/paramspec-versioning.md`. Сохранённый
документ логически разделяется на domain payload и server-owned `catalog`
metadata через `src/paramspec_versioning.py`, оставаясь плоским JSON ради
совместимости. Reads могут игнорировать и метить только неизвестные extension-
поля; невалидные известные поля и чужая `schemaVersion` отклоняются. Writes
всегда strict и атомарны. Перед любой массовой записью обязателен отдельный
разрешённый batch-план с backup manifest, dry-run, history/revisions и rollback.

### Новый архетип или изменение генератора

1. Зафиксировать входной контракт и конструктивные инварианты.
2. Реализовать генератор и зарегистрировать его в `generators/registry.py`.
3. Не принимать координаты от LLM; все placement вычислять из ParamSpec.
4. Проверить панели, ориентацию, кромки, коллизии, BOM, фурнитуру и присадки.
5. Добавить минимальный, типовой и граничный ParamSpec.
6. Проверить, что изменения не затронули остальные архетипы.

### Новая AI-команда или узел

1. Сначала определить типизированный вход/выход и запрещённые возможности.
2. Добавить/изменить node и capability schema в `prompt_registry.py`.
3. Обновить отдельный prompt-файл и повысить его версию.
4. Передавать только минимально нужный контекст.
5. Валидировать ответ Pydantic-моделью; применять атомарно.
6. Добавить trace узла, provider/model, prompt id/version, usage, outcome и code.
7. Покрыть success, malformed response, provider error, отказ gate и попытку
   изменить несвязанные поля.

Не возвращаться к одному общему prompt: маршрутизация, создание, правка,
диагностика и вопросы имеют разные полномочия и разные схемы ответа.

### Новый provider LLM/vision

Provider обязан поддерживать общий внутренний контракт и bounded timeout без
скрытых бесконечных retries. Секреты берутся только из env/secret storage.
Нужны offline mocks/contract tests; live-тест выполняется отдельно, с лимитом
стоимости и без сохранения пользовательского содержимого. Переключение модели
не должно менять полномочия узла.

### Новый вид присадки/фурнитуры

Одновременно обновить расчёт в `hardware.py`, геометрический контроль,
`fasteners3d.py::_PURPOSE_KIND`, viewer-группы и проверки completeness/drilling.
Проверить обе соединяемые детали и parity отверстий, а не только видимый крепёж.

### Studio/API/3D

API ошибки должны иметь корректный HTTP status, стабильный `code` (для
совместимости допустим alias `error_code`) и `trace_id`. Пользователь получает
понятное действие, разработчик — диагностический код. UI не должен сохранять
невалидный объект, оставлять на экране модель предыдущего объекта как будто это
новая, или скрывать ошибку ответом HTTP 200.

## 7. Trace, логи и приватность

Для AI pipeline должны быть видны как минимум:

- узлы и их порядок;
- provider/model и prompt id/version;
- input/output/total token usage, если provider их сообщил;
- результат валидации/gate и стабильный error code;
- одна сквозная ссылка `trace_id` от HTTP-ответа до серверного лога.

В trace/log запрещены: base64 изображения, полный текст ТЗ, полный prompt с
пользовательскими данными, полный ParamSpec, ФИО/контакты и секреты. Используй
счётчики, типы, версии, хэши и коды. Серверный exception пользователю напрямую
не отдавать; в UI — безопасное сообщение + code + trace id.

Live trace-тест не заменяет unit/regression. Он нужен для ответа на вопрос «что
реально решил provider», проводится на неперсональном fixture, без persistence
и с заранее ограниченными запросами/стоимостью.

Версионируемый offline trace replay — отдельный обязательный контур для
create/edit/diagnosis/repair изменений. Dataset хранит только неперсональные
команды, ссылки на fixture и сохранённые структурированные node outputs. Replay
не вызывает provider: записанный результат проходит текущие Pydantic-контракты,
typed reducer, генератор и production gate, после чего сравниваются node outputs,
diff, число деталей/присадок и статусы всех проверок. Сравнимый JSON-отчёт должен
содержать prompt/model версии и стабильные digests, но не raw prompt, полный
пользовательский ParamSpec, изображения или секреты.

## 8. Минимальная матрица проверки

Для любого изменения движка выбери профильные тесты, затем всегда выполни оба
полных gate из `tools/basis/AGENTS.md`.

| Изменение | Обязательные профильные проверки |
|---|---|
| ParamSpec/schema | `test_paramspec_pydantic.py`, все catalog validation, migration tests |
| create/edit AI | `test_prompt_registry.py`, `test_spec_chat.py`, `test_edit_operations.py`, `test_studio_graph.py` |
| trace/eval dataset | `python main.py trace-eval`, `test_trace_replay.py`; только offline, live provider не является CI-гейтом |
| import/API | профильный HTTP-тест Studio: status, code, trace id, отсутствие записи при ошибке |
| generator | тест архетипа, geometry/consistency, production gate, regression/golden |
| drilling/hardware | hardware, hardware_geometry, drilling_check, CFRN holes parity |
| Studio/viewer | API/contract-тесты, webviewer, ручной smoke текущего и соседнего сценария |
| B3D/CFRN | encoding, verify, production reference; платный cloud только по разрешению |

Критические негативные сценарии: provider недоступен; ответ не JSON; невалидная
операция; попытка несвязанной мутации; красный gate; конфликт ревизии; старый
каталоговый объект; переключение между объектами после ошибки.

## 9. Ветка, review, release и rollback

1. Сверить `origin/master`, работать в отдельной `codex/<task>` ветке/worktree.
2. До кода зафиксировать ожидаемый контракт, риск и способ проверки.
3. Не смешивать визуальные/чужие изменения с задачей движка.
4. Выполнить профильные тесты, затем `python -m pytest tests/ -q` и
   `python -m tests.regression`.
5. Просмотреть diff, особенно schema, goldens, `studio.py` и миграции.
6. Коммит/PR/push/deploy — только в рамках выданного разрешения. В PR указать
   trace/evidence, миграцию, риски и rollback.
7. После deploy: health-check, открыть существующий объект, создать новый из
   fixture ТЗ, выполнить одну правку и проверить trace/error path.
8. При красном smoke откатить релиз к последнему известному SHA; не чинить
   production вручную поверх незафиксированного кода.

## 10. Короткий checklist перед завершением

- [ ] Прочитан этот runbook и профильные правила.
- [ ] Create/edit/query имеют разные полномочия и схемы.
- [ ] LLM не вычисляет производственные координаты и не меняет лишние поля.
- [ ] Изменение применяется copy-on-write и только после полного gate.
- [ ] Старые ParamSpec обработаны явно; скрытой массовой миграции нет.
- [ ] Ошибка имеет HTTP status, code и trace id; логи privacy-safe.
- [ ] Добавлены success и negative regression tests.
- [ ] Полный pytest и regression зелёные.
- [ ] Документы обновлены, если изменился контракт.
- [ ] Deploy и платные вызовы имеют явное разрешение и план rollback.
