# Идентичность, компании и доступы

Этот документ обязателен для задач про логин, пароль, пользователя, сотрудника,
компанию, роль, приглашение, администратора, поддержку, аудит или SaaS-доступ.

## Главный принцип

Экран входа сам по себе не делает Studio многопользовательским. Доступ считается
реализованным только когда сервер на **каждом** запросе знает:

1. кто действует (`actor_user_id`);
2. в контексте какой компании (`organization_id`);
3. какое конкретное право требуется (`permission`);
4. к какому объекту относится действие;
5. какое событие записано в аудит.

Скрытая кнопка, роль в JavaScript, `organization_id` из body/header/query и UUID,
который «сложно угадать», авторизацией не являются.

## Разделение областей

- **Platform realm**: сотрудники Akeda. Роли `platform_owner` и
  `platform_support` не являются ролями клиентской компании.
- **Organization realm**: сотрудники одной компании. Связь хранится как
  membership пользователя в организации.
- **Support session**: отдельная временная связь platform-актора с компанией.
  Она не подменяет личность сотрудника компании.

Один пользователь может состоять в нескольких организациях. Его права всегда
вычисляются для конкретного membership и конкретного объекта.

## Роли первой версии

| Роль | Назначение |
|---|---|
| `owner` | Владелец компании: вся работа компании и производство; состав сотрудников меняет Akeda |
| `admin` | Управление проектами и настройками без управления сотрудниками и передачи владения |
| `designer` | Создание и изменение проектов, AI-команды, версии, чертежи и бесплатные экспорты |
| `technologist` | Производственная проверка, BOM, `.cfrn`; платные операции — только с отдельным правом |
| `reviewer` | Просмотр и согласование без изменения ParamSpec и производства |

В обработчиках проверяются permissions, а не строки ролей. Минимальный словарь:

- `organization.read`, `organization.manage`;
- `member.read`, `member.invite`, `member.manage`;
- `project.read`, `project.create`, `project.write`;
- `ai.run`, `audit.read`;
- `production.export`, `production.build`;
- `support.grant`.

## Неприкосновенные инварианты

- Каждая сущность компании имеет `organization_id`: проект, ревизия, файл,
  preview, AI-команда, job, export, build, лимит и событие аудита.
- Tenant-контекст выводится из проверенной серверной сессии. Клиент не выбирает
  его произвольным ID.
- Доступ по умолчанию запрещён; разрешение проверяется на каждом чтении и
  изменении, включая файлы и фоновые job.
- Общие `paramspecs/`, `out/`, `CHAT_HISTORY` и mutable `_Studio.spec_path` нельзя
  выдавать за tenant isolation.
- Пароли хранятся только как медленный salted hash. Platform owner Akeda может
  выпустить новый шестизначный буквенно-цифровой стартовый пароль; raw-значение
  показывается один раз и никогда не читается из базы. Существующий пароль
  посмотреть нельзя — только отозвать и заменить новым.
- Приглашения и reset-токены одноразовые, ограничены по времени и хранятся как
  hash. После принятия/сброса токен невозможно использовать повторно.
- Session ID — случайный opaque token в `HttpOnly` cookie; в БД хранится его
  hash. Изменяющие запросы защищены CSRF-проверкой и проверкой Origin.
- Смена пароля, блокировка пользователя/компании и изменение критичной роли
  отзывают соответствующие активные сессии.
- Audit append-only. Пароли, raw-токены, ключи API, полные изображения и полные
  ParamSpec в него не записываются.
- `src/webviewer.py` и утверждённая `MebelScene` не меняются при внедрении доступа.

## Просмотр компании из Akeda

Platform owner не заполняет тикет, причину или срок. Из карточки клиента он
нажимает `Открыть компанию` и попадает в тот же продуктовый интерфейс, который
видит сотрудник: каталог, изделия, AI-история и производственные данные.

Это не скрытая подмена сотрудника:

1. актором остаётся личная platform-учётка;
2. выбранная компания хранится в серверной сессии, а не принимается от клиента
   как доверенный `organization_id`;
3. сверху постоянно видна полоса `Вы просматриваете компанию … от имени Akeda`;
4. каждое чтение и изменение записывает настоящего platform-актора;
5. `Вернуться в админку` завершает контекст компании;
6. технический expiry остаётся внутренней защитой и не превращается в форму для
   пользователя.

До tenant-миграции разрешены только уже изолированные данные компании. Каталог,
чаты и Studio нельзя подключать к этому переходу через общие `paramspecs/` и
process-global состояние.

## Демо-компания

- Базовый demo-шаблон неизменяем.
- Каждый вход создаёт отдельную ephemeral sandbox-сессию с собственной копией
  проектов и AI-истории.
- Изменения одного посетителя не видны другому и никогда не перезаписывают
  исходный шаблон.
- Выход, expiry или cleanup уничтожает overlay; следующий вход снова получает
  исходное состояние.
- Демо-запросы к AI имеют отдельные лимиты и не запускают платные production
  операции или экспорт реальных файлов.

## Локальная разработка

- Identity/admin server по умолчанию слушает только loopback.
- Bootstrap platform admin разрешён только когда база пуста, `STUDIO_PUBLIC!=1`
  и секрет передан через окружение. В коде нет дефолтного пароля.
- В первой коммерческой версии сотрудников централизованно создаёт только
  platform owner Akeda: логин равен почте, email-доставка и проверка почты не
  выполняются. Старый invitation flow остаётся совместимым техническим контуром,
  но не показывается в основном интерфейсе.
- Dev-режим не ослабляет permission, session, CSRF, expiry или audit checks.

## Гейты перед публикацией

- negative tests между двумя компаниями для каждого object endpoint;
- unauthenticated/disabled/expired session tests;
- role-demotion и membership-removal tests;
- invite/reset replay tests;
- CSRF и чужой Origin tests;
- company-view actor/banner/audit tests;
- demo-session isolation/reset/cleanup tests;
- отсутствие diff в `src/webviewer.py`;
- миграция и откат протестированы на копии production-данных;
- platform admin защищён MFA/passkey перед реальным клиентским доступом.
