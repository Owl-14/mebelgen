# AGENTS.md — обязательные правила работы с репозиторием

Этот файл действует для **всего репозитория** `Owl-14/mebelgen` и должен быть
прочитан в начале каждой новой задачи, нового чата и нового worktree.
Файлы `AGENTS.md` ниже по дереву добавляют предметные правила и не отменяют
ограничения этого файла.

Главная цель: несколько людей и агентов могут работать параллельно, не теряя
чужие изменения, не превращая продакшен в источник кода и не выкатывая
непроверенные изменения.

## 0. Что означают команды пользователя

- **«Работаем локально», «покажи локально», «сделай демку»** — изменения
  остаются в ветке задачи и на локальном сервере. Коммит, push, PR, merge и
  deploy без отдельной команды не выполняются.
- **«Закоммить»** — создать проверенный коммит только в текущей ветке.
- **«Отправь в GitHub», «сделай PR»** — push ветки и PR; это не разрешение на
  merge или deploy.
- **«Выгружай», «публикуй», «выкатывай всё»** — полный обязательный цикл:
  проверки → коммит → push → PR → зелёный CI → merge в `master` → deploy
  именно merge SHA → post-deploy smoke. Нельзя останавливаться после push или
  выкатывать SHA, которого нет в `master`.

Если формулировка неоднозначна, внешние изменения не делать до уточнения.

## 1. Источник правды и среды

Приоритет источников:

1. `origin/master` в `https://github.com/Owl-14/mebelgen` — принятая версия кода.
2. Отдельная ветка задачи — незавершённая работа по одной теме.
3. Локальный worktree — рабочее место конкретной задачи.
4. `https://studio.akeda.ru` — развёрнутый артефакт, **не источник кода**.

Принятый код и production обязаны сходиться: `/version` может указывать только
на SHA, достижимый из `origin/master`. Развёртывание ветки задачи до merge
запрещено.

Продакшен находится на `80.66.89.3`; приложение развёрнуто в
`/opt/bazis/basis` как копия `tools/basis`, без `.git`. Никогда не вести
разработку правкой файлов на сервере и не копировать их обратно как «новую
версию». Порядок всегда такой:

```text
локальная ветка → проверки → PR → merge → явный deploy утверждённого SHA
```

Каталоги-снимки рядом с репозиторием (`mebelgen-current`, архивы, выгрузки)
не являются рабочими копиями и не должны использоваться вместо Git checkout.

## 2. Обязательный старт каждой задачи

До редактирования:

1. Найти корень: `git rev-parse --show-toplevel`.
2. Прочитать этот файл и ближайший `AGENTS.md` в целевом подкаталоге.
3. Проверить `git status --short --branch`. Незнакомые изменения считать
   чужими; не удалять, не откатывать и не включать в свою задачу.
4. Выполнить `git fetch --prune origin`.
5. Убедиться, что работа идёт в отдельной ветке от свежего `origin/master`.
6. Зафиксировать границы задачи: какие файлы меняем, какие проверки запускаем,
   нужен ли вообще сервер.

Если worktree грязный и изменения пересекаются с задачей — остановиться и
согласовать работу. Не маскировать проблему `stash`, reset или «временным»
удалением чужих файлов.

## 3. Ветки, worktree и параллельные чаты

- Одна задача = одна ветка = один worktree.
- Для Codex использовать `codex/<короткая-тема>`. При наличии тикета допустимо
  `codex/AKD-123-короткая-тема`.
- Для общей команды допустимы `feat/AKD-123-*`, `fix/AKD-123-*`,
  `docs/AKD-123-*`.
- Не работать напрямую в `master`.
- `master` защищён: изменения попадают туда только через PR и успешный CI.
- Не использовать одну ветку одновременно в двух чатах.
- Не переключать ветку в worktree другого человека или агента.
- Не делать force-push общей ветки и не переписывать чужие коммиты.
- Перед передачей задачи сообщить: ветку, базовый SHA, изменённые файлы,
  пройденные проверки и оставшиеся риски.

Файлы с высокой вероятностью конфликтов требуют явного владельца на время
задачи:

- `tools/basis/src/studio.py`;
- `tools/basis/src/webviewer.py`;
- `tools/basis/schema/*`;
- `tools/basis/materials/baza_materiala.json`;
- regression goldens и общие `paramspecs/`;
- `.github/workflows/*` и `tools/basis/ops/*`.

Подробно: [docs/TEAM_WORKFLOW.md](docs/TEAM_WORKFLOW.md).

## 4. Границы полномочий по умолчанию

Без явной просьбы пользователя **не**:

- коммитить, пушить, открывать/мержить PR;
- деплоить, перезапускать сервисы или менять nginx/systemd;
- менять пароль, SSH-доступ, firewall, DNS или сертификаты;
- вызывать платные API БАЗИС/раскроя;
- обновлять goldens «чтобы тест стал зелёным»;
- редактировать `.env`, копировать или выводить секреты;
- менять пользовательские изделия на сервере.

Разрешены локальная разработка, чтение Git/GitHub/сервера, локальные тесты и
безопасная диагностика в пределах задачи.

Запрещены разрушительные команды (`git reset --hard`, `git clean -fd`,
необоснованный `rm -rf`), force-push и ручная замена файлов на продакшене.

## 5. Карта проекта и локальные правила

| Область | Что это | Что читать |
|---|---|---|
| `tools/basis/` | основной продукт: ParamSpec, генераторы, Studio, `.cfrn/.b3d` | `tools/basis/AGENTS.md`, `tools/basis/rules/*` |
| `input_specs/` | исходные ТЗ и эталонные входные данные | локальные README; менять только по явной задаче |
| `docs/` | исследования и общая документация | не выдавать исследование за production-контракт |
| `.github/workflows/` | обязательные CI-гейты | изменение требует отдельной проверки CI |
| `tools/basis/ops/` | systemd/nginx/deploy/runbook | только инфраструктурная задача |

Правила по типам задач и команды проверки:
[docs/TASK_PLAYBOOKS.md](docs/TASK_PLAYBOOKS.md).

Старый Blender-конвейер `tools/refsheets` удалён из актуального дерева. Не
восстанавливать его из истории и не использовать как источник архитектуры,
геометрии или UI Akeda Studio. Источник правды — `tools/basis/AGENTS.md` и
`tools/basis/rules/`.

## 6. Данные, артефакты и секреты

- `.env`, токены, пароли, приватные ключи и содержимое секретных переменных
  никогда не коммитить и не вставлять в логи/PR/чат.
- Можно перечислять **имена** переменных окружения без их значений.
- `out/`, временные архивы, кэши, `__pycache__`, `.previews`, локальные рендеры
  и скачанные зависимости не включать в коммит без явной причины.
- `input_specs/` считать исходными данными пользователя; не переформатировать
  массово и не удалять.
- `paramspecs/` и `projects/` могут содержать тестовые/пользовательские изделия.
  Менять только файлы, входящие в задачу.
- `materials/baza_materiala.json` не форматировать целиком.
- Генерируемые goldens обновлять только после проверки смыслового изменения и
  описывать его в PR.

## 7. Реализация

- Сначала найти существующий путь и расширять его, а не создавать параллельную
  архитектуру.
- Держать diff минимальным: не смешивать рефакторинг, форматирование,
  документацию и новую функцию без необходимости.
- Сохранять обратную совместимость ParamSpec, проектов и публичных маршрутов,
  если миграция не является явной частью задачи.
- Не выдумывать материалы, артикулы, фурнитуру и производственные правила.
- Координаты деталей рассчитывает детерминированный генератор, не LLM.
- В `studio.py` и `webviewer.py` учитывать, что HTML/JS встроены в Python:
  проверять кавычки, фигурные скобки, сериализацию и браузерный синтаксис.
- Любая новая ветка поведения должна иметь тест или объяснение, почему
  автоматический тест неприменим.

## 8. Проверки перед передачей

Минимум для изменений в `tools/basis`:

```bash
cd tools/basis
python -m pytest tests/ -q
python -m tests.regression
```

Сначала можно запускать целевые тесты, но перед merge обязательны оба полных
гейта. Для UI дополнительно нужен локальный smoke-test Studio и скриншоты
затронутых состояний.

Перед завершением:

1. `git diff --check`;
2. `git status --short`;
3. проверить diff на секреты, случайные бинарники и чужие файлы;
4. перечислить фактически выполненные проверки и то, что не проверено.

Нельзя говорить «всё работает», если проверена только часть.

## 9. Коммиты и PR

Коммитить/пушить только по явной просьбе.

- Один логический коммит — одна причина изменения.
- Если есть Linear-задача, сообщение содержит `AKD-<N>`.
- PR должен содержать: проблему, решение, область изменений, проверки,
  скриншоты UI, риски, миграцию/откат и необходимость деплоя.
- Не включать в PR `DEPLOY_SHA`, локальные настройки и артефакты.
- Merge только после зелёного CI и разрешения конфликтов с актуальным
  `master`.

## 10. Продакшен и деплой

Продакшен трогать только по явному запросу на deploy/диагностику.
Авторитетный runbook:
[tools/basis/ops/runbook.md](tools/basis/ops/runbook.md).

Перед deploy:

1. убедиться, что нужный SHA принят и рабочее дерево чистое;
2. записать текущий `/version` как точку отката;
3. проверить свежий backup пользовательских `paramspecs`;
4. пройти тесты;
5. не переносить `.env`, `/opt/bazis/out` и серверные `paramspecs`.

Deploy выполнять только штатным `tools/basis/ops/deploy-update.sh`, задав
`BAZIS_DEPLOY_KEY`, если ключ лежит не в стандартном пути.

После deploy обязательны:

```bash
curl -fsS https://studio.akeda.ru/healthz
curl -fsS https://studio.akeda.ru/version
ssh <host> 'systemctl is-active bazis && journalctl -u bazis -n 50 --no-pager'
```

Дополнительно сравнить `/version` с merge SHA и убедиться, что этот SHA
достижим из `origin/master`. Несовпадение считается незавершённым deploy, даже
если сайт визуально открывается.

Также выполнить ручной smoke-test изменённого пользовательского сценария.
При сбое остановиться и откатить известный предыдущий SHA; не чинить прод
серией ручных правок.

## 11. Definition of Done

Задача завершена только когда:

- выполнена заявленная область, без случайных соседних изменений;
- добавлены/обновлены тесты и документация;
- обязательные проверки прошли;
- diff просмотрен;
- пользователь получил точный отчёт;
- для командной передачи указаны ветка и SHA;
- продакшен либо не затрагивался, либо deploy и post-deploy проверены отдельно.
