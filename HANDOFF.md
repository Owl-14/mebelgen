# MEBELGEN handoff

Дата фиксации контекста: 2026-06-29.

## Главная цель

Сделать производственный инструмент для мебельной компании:

```text
ТЗ клиента -> структурированный FurnitureSpec JSON -> технический лист A4
```

Сначала генерируем красивые клиентские визуализации на уровне референсов ME-RA,
но в собственном шаблоне и под брендом Constante:

- вид спереди / сверху / 3D-изометрия по необходимости;
- размеры;
- стрелки-выноски;
- материалы и описание;
- штамп.

Следующий большой этап после визуализаций: автоматизация сборки изделия в
Базис-Мебельщик. Сейчас он вынесен в отдельный исследовательский контур: не
мешаем его с клиентским листом, но уже фиксируем API, формат производственного
JSON и первый импортёр.

## Ключевое архитектурное решение

Финальную картинку не должна рисовать нейросеть. Финальную картинку строит детерминированный рендерер:

- Three.js строит параметрическую 3D-модель;
- SVG поверх canvas рисует размеры, стрелки и подписи;
- HTML/CSS собирает лист A4;
- позже Playwright/headless Chrome будет экспортировать PNG/PDF.

AI нужен как управляющий слой:

- разобрать ТЗ;
- выбрать архетип мебели;
- вернуть строгий `FurnitureSpec JSON`;
- посмотреть готовый PNG;
- предложить правки, если композиция плохая.

API Gemini/OpenAI пока не подключаем. Работаем в `mock/dev` режиме, чтобы довести контракт, рендер и правила.

## Текущее состояние визуального листа

Лист `demo/three-spike` уже не копирует чужой штамп: бренд в шаблоне заменён на
Constante, добавлена собственная мягкая рамка/акцентная полоса и нижний блок
материалов.

Последние важные правки renderer:

- камера подгоняется по реальному bounding box модели, а не по сырым габаритам
  из ТЗ, поэтому верх столов/шкафов больше не должен обрезаться;
- фронтальный canvas выровнен с SVG-слоем без старого сдвига `44px`;
- материалы получили процедурную фактуру плиты/древесины и видимые кромки;
- выноски раскладываются по левому/правому полю и используют короткий текст,
  полный состав остаётся в нижнем блоке материалов;
- при ошибке WebGL/Three.js лист показывает сообщение вместо пустой белой зоны.

Дополнительные правки последней итерации:

- фронтальный вид сделан почти прямым, но с лёгким объёмом за счёт камеры,
  света, толщин и теней; это ближе к референсам ME-RA, где стол/тумба выглядят
  живыми, но не превращаются во вторую изометрию;
- для шкафов высокий фронт остаётся почти плоским, потому что при прямом виде
  корпусная мебель естественно читается как фасад;
- для подкатных тумб колёсики заменены с крупных цилиндров на низкие
  мебельные ролики/площадки;
- для изделий с внутренним наполнением в изометрии добавлены вертикальные
  размерки примерного шага полок;
- query/cache-buster листа поднят до `constante-sheet-4`, чтобы браузер не
  показывал старый renderer.

Рекомендованный будущий формат доставки: веб-страница проекта как источник
правды плюс кнопка PDF/PNG-экспорта конкретной версии. Подробно:

## Текущие тренировочные кейсы

Импортируется 8 изделий из `Кабинеты ДРЧК`:

1. `desk_panel` — Стол рабочий в кабинете 1800x800x750.
2. `drawer_unit` — Тумба для документов 1100x450x750.
3. `wardrobe` — Шкаф комбинированный 1000x400x1800.
4. `wardrobe` — Шкаф для документов 1000x400x1800.
5. `coffee_rect` — Журнальный стол 1000x450x450.
6. `cabinet` — Средняя тумба тип 2 800x400x900.
7. `coffee_round` — Стол кофейный тип 1 Ø500x420.
8. `coffee_fluted` — Стол кофейный Ø400x400.

## Правила выносок

Не дублируем одну и ту же информацию в двух видах.

- Фронтальный вид: основные габариты, фасады, видимые материалы, цоколь, ящики, двери.
- 3D-изометрия: глубина, скрытые узлы, открытые двери, внутреннее наполнение, детали, которые невозможно понятно показать спереди.
- Нижний блок материалов: полный текстовый список без стрелок.

Пример: тумба с ящиками подписывает корпус/ящики/цоколь на фронте, а изометрия оставляет только объём и глубину.

## Важный вывод по шкафам

Для сложных изделий нельзя использовать одну и ту же 3D-модель во всех видах.

Нужны view presets / scene states:

- `wardrobe_closed_front` — закрытый фасад и габариты.
- `wardrobe_open_iso_with_clothes` — открытые двери, штанга, одежда, обувная полка.
- `cabinet_open_iso` — открытая тумба/шкаф с полками.
- `drawer_unit_front` — фронт с ящиками и замком.

Сейчас для комбинированного шкафа уже есть первый вариант: фронт закрытый, изометрия открытая.

## База производства

База нужна. Лучший формат для начала:

- `.xlsx` или `.csv` по материалам;
- `.xlsx` или `.csv` по фурнитуре;
- таблица типовых шаблонов изделий;
- таблица производственных правил;
- папка с PDF/картинками/каталогами, привязанными к id из таблиц.

AI должен не выдумывать материалы, а выбирать реальные позиции из этой базы и возвращать их id в `FurnitureSpec JSON`.

## БАЗИС-контур

Добавлен отдельный исследовательский пакет:

- `BASIS_WORKFLOW.md` — полный путь от `FurnitureSpec` до
  `BasisProductionModel` и `.b3d`;
- `BASIS_PREVIOUS_REPO_REVIEW.md` — разбор старого репозитория
  `zazabag/mebel-bazis` и что из него переносить;
- `BASIS_APILIST_RESEARCH.md` — проверка публичного АпиЛист/Cutting API и
  ограничений по `ExecuteClientScript`;
- `basis/scripts/detect_basis_api.js` — диагностический скрипт для запуска
  внутри БАЗИС-Мебельщика;
- `basis/scripts/import_basis_model.js` — минимальный импортёр
  `BasisProductionModel` с прямоугольными панелями, материалами, кромкой и
  сохранением `.b3d`;
- `basis/samples/wardrobe-basic.json` — тестовый производственный JSON;
- `basis/apilist/check_tasks_api.mjs` — утилита для проверки публичных задач
  АпиЛист через `BAZIS_API_KEY`.

Главный вывод: публичный OpenAPI подтверждает конвертации и Cutting API, но не
подтверждает публичный `POST` для запуска клиентского JS-скрипта. Надёжный MVP
для производства пока такой:

```text
ТЗ -> FurnitureSpec -> BasisProductionModel -> локальный/операторский БАЗИС-импортёр -> .b3d -> Cutting API
```

Полностью облачный `ТЗ -> АпиЛист ExecuteClientScript -> .b3d` оставляем как
гипотезу до ответа БАЗИС-Центра или проверки личного кабинета.
