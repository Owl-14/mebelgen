# База правил для тумбочек / тумб (TUMBA_RULES)

> Этот файл — **ограниченная база знаний** для изделий типа «тумба», «тумбочка», «тумба под …» и близких по форме шкафчиков с ящиками/дверцами.  
> Использовать ТОЛЬКО когда в ТЗ явно указано, что изделие — тумба/тумбочка/шкафчик подобного класса.

---

## 1. Когда включать TUMBA_RULES

**Включать**, если в ТЗ встречаются слова (с учётом падежей и опечаток):

- «тумба», «тумбочка», «тумба под ТВ», «тумба модератора», «тумба для …»
- «тумба с ящиками», «тумба с дверцей», «тумба прикроватная», «тумба под раковину» и т.п.

**Не включать**, если изделие — явно другое:

- «стойка охраны», «кассовая зона», «ресепшн», «барная стойка»
- «кашпо», «стеллаж», «шкаф купе», «гардероб», «панель», «перегородка» и т.п.

Если есть сомнение — сначала трактовать как **не тумба**, и только при явном подтверждении текста включать TUMBA_RULES.

---

## 2. Что входит в базу для тумб

TUMBA_RULES опирается на отработанный пример `examples/moderator_cabinet.json`, но переносит только **методику**, а не числа.

### 2.0. Отличие тумбы от «просто корпуса»

Тумба обычно содержит один или несколько из элементов:

- фасады (ящики и/или дверь) на передней плоскости;
- технологические зазоры фасадов (обычно 2 мм);
- зоны: стек ящиков, открытая секция, секция с дверью;
- фурнитура: ручки, направляющие, петли.

Главная особенность: требуется корректно рассчитать **фасадную полосу** по Y и не допустить пересечений фасадов с полками/задней стенкой.

### 2.1. Система координат и ориентации

- Система `basis_mebelshik`: (0,0,0) — левый нижний передний угол корпуса.
- `placement` обязателен для каждой панели, `rotation` всегда 0.
- `basis_orientation`:
  - `horizont` — дно, крышка, полки, дно ящика → `NewPanel(spanX, spanZ)`.
  - `vertical` — боковины, перегородки, боковины ящика → `NewPanel(spanZ, spanY)`.
  - `front` — фасады, задняя, задняя ящика → `NewPanel(spanX, spanY)`.

### 2.2. Корпус тумбы (алгоритм)

Обозначения: W, D, H — габарит; T — толщина ЛДСП; Hleg — высота опор (0, если нет).

```
Y_дно_низ  = Hleg
Y_дно_верх = Hleg + T
Y_бок_низ  = Hleg + T
Y_бок_верх = H - T          // низ крышки
Y_крыш_низ = H - T
Y_крыш_верх = H

Дно/крышка:  x1=0, x2=W,  z1=0, z2=D
Боковины:    x1=0 / x2=W-T, y от Y_бок_низ до Y_бок_верх, z1=0, z2=D
Задняя:      x1=T, x2=W-T, y как боковины, z2=D, z1=D-T
```

### 2.3. Зазоры по Z (фасады и полки)

- Фасады: обычно z `0…T` (как правило `0…16`).
- Полки/перегородки: z T…(D−Tзад), чтобы не пересекать фасады и заднюю.

### 2.3.1. Обязательные правила «не пересекать»

- Полка/перегородка **не должна** входить в объём фасада: `z2 ≤ D - Tзад` и `z1 ≥ T`.
- Задняя стенка **не должна** пересекаться с полками: задняя `z1 = D - T`, полки `z2 = D - T`.
- Фасады: `z1 = 0`, `z2 = T` — передняя плоскость.

#### 2.3.2. Если фасады “выпирают” в БАЗИС

В некоторых окружениях БАЗИС визуально удобнее считать фасад “стоящим снаружи”:

- фасад: `z1 = -T`, `z2 = 0`
- корпусные панели: `z1 = T` (или `z1 = 0`, если фасад вынесен в `-T..0`)

Это не меняет логику стыков, но убирает эффект “дверь торчит вперёд”. Если видите выпирание — используйте вариант `-T..0` для `door_front`/`drawer_front`.

### 2.4. Фасады тумбы по высоте (N ящиков)

Для зоны фасадов по высоте (от Y_фасад_низ до Y_фасад_верх):

```
Y_фасад_низ  = Y_бок_низ + gap
Y_фасад_верх = Y_бок_верх - gap
H_полоса     = Y_фасад_верх - Y_фасад_низ
H_одного     = (H_полоса - (N-1)*gap) / N

для k = 0..N-1:
  y1_k = Y_фасад_низ + k*(H_одного + gap)
  y2_k = y1_k + H_одного
```

`gap` — `constraints.drawer_gap` или `default_gap` (обычно 2 мм).

### 2.5. Левая секция с выдвижными ящиками (паттерн)

Если в тумбе есть **стек ящиков** (как `left_drawers`):

- **Никаких стационарных горизонтальных перемычек между ярусами.**
- Каждый ящик — **короб**: дно, 2 боковины, задняя, фасад.
- Ярус `k` привязывается к своей паре координат фасада `y1_k..y2_k` (см. выше).

Короб в общем виде (по внутренней ширине секции `Sw` и глубине дна `Dd`):

```
Дно:       x = X_секция_внутр,   ширина Sw,  z = z_дно..z_дно + Dd
Бок. лев.: x = X_секция_внутр..+T,          z как дно
Bок. прав: x = X_секция_внутр + Sw - T .. X_секция_внутр + Sw
Задняя:    x между боковинами, z смещён назад (под направляющие)
```

Конкретные числа для модератора — смотреть только как пример в `CABINET_DIMENSIONS.md`, **не копировать**.

### 2.5.1. Типичная ошибка (которую нельзя допускать)

Сделать «полки-перемычки» между ящиками (стационарные горизонтальные панели).  
Вместо этого: каждый ящик — отдельный выдвижной короб, а в корпусе между ярусами — пустое пространство.

### 2.6. Средняя/правая секции

- Открытые секции: одна или несколько полок с теми же правилами по Z и Y.
- Секцию с дверью моделировать как: поле `doors[]` + панель `door_front` с зазорами по периметру (обычно 2 мм).  
Зазоры — как у фасадов ящиков (верх/низ/бок 2 мм).

### 2.6.1. Частая ошибка: “верх открыт, а двери на всю высоту”

Если в тумбе **есть полка, которая делит корпус на верхнюю открытую зону и нижнюю закрытую**, то `door_front` закрывает **только нижний проём**:

- пусть полка: `y1_shelf..y2_shelf`
- тогда дверь: `y2_door = y1_shelf - gap` (обычно `gap=2`)
- низ двери: `y1_door = Y_бок_низ + gap`

Верхняя зона остаётся без фасада.

### 2.6.2. Кейс из практики: “тумба 1200×(350/270)×740 под оргтехнику”

Симптомы, которые ловили на реальном ТЗ:

- глубина задана как **350/270** → столешница глубже корпуса;
- верхний ярус **открыт**, нижний закрыт дверями;
- “некрасивый угол” над дверьми, если полка не доходит до плоскости фасада;
- перегородка/полка “входит в задник”, если не остановить по Z.

Ниже — рабочие правила, которые применили, чтобы модель в БАЗИС выглядела как на картинке.

#### A) Две глубины: столешница + корпус (без «разворотов»)

Если ТЗ вида `D_total / D_carcass` (например 350/270):

- **корпусные панели** (дно/бок/перегородки): `z 0..(D_carcass - T_back)`
- **задник**: `z (D_carcass - T_back)..D_carcass`
- **столешница**: допускается свес вперёд: `z (-overhang)..D_carcass`

Пример: `D_carcass=270`, `T_back=3.2` → корпус `z2=266.8`, задник `266.8..270`.

#### B) Двери “врезные в проём” (чтобы не висели в воздухе)

Если по виду изделия двери должны быть **внутри проёма**, а не накладные:

- по X дверь “внутри” секции с зазором `gap=2`:
  - слева: `x1 = T + gap`, `x2 = X_перегородки - gap`
  - справа: `x1 = X_перегородки + T + gap`, `x2 = W - T - gap`
- по Y: `y1 = Y_бок_низ + gap`, `y2 = y1_shelf - gap` (см. §2.6.1)
- по Z: `z 0..T_f` (обычно `0..16`)

Это убирает “зазор от стенок” и ощущение “дверь висит”.

#### C) Полка над дверьми должна “заходить” на фасад (красивый угол)

Если над дверьми виден “ступенчатый угол”, делаем так:

- полка верхней открытой зоны тянется вперёд до плоскости фасада: `z1 = 0`, `z2 = D_carcass - T_back`
- в этом случае правило §2.3.1 `z1 ≥ T` **не применяем к этой полке**, потому что она *намеренно* перекрывает зону фасада по Z.

Практически: полка стоит **выше дверей по Y**, поэтому пересечения объёма с фасадами нет (пересечение по Z допустимо, т.к. по Y они разнесены).

#### D) Перегородки и полки не должны входить в задник

Жёсткое правило:

- все корпусные панели, которые доходят до задней грани, ограничиваем `z2 = D_carcass - T_back`
- задник занимает последний слой `T_back`

Иначе перегородка “входит” в задний фасад/ДВП.

#### E) Как проверять

После правок по этому кейсу:

- прогнать `finish` (схема + геометрия);
- визуально в БАЗИС: двери в проёме, полка красиво закрывает угол, перегородка не в заднике.

### 2.7. Фурнитура тумбы

В `hardware`:

- `handles` — ручки (обычно по количеству фасадов ящиков/дверей).  
  - `count` > 0 → скрипт ставит их через `buildHandles`.
  - `offset_from_top` — отступ от верха фасада.
- `drawer_guides` — направляющие ящиков (опционально, когда появится база).  
  Сейчас можно оставлять пустым или не задавать (скрипт учитывает это).

Реальные `furniture_encoded` ручек/направляющих — только после выбора в БАЗИС (или если в ТЗ есть конкретный артикул из вашей базы).

### 2.8. Ручки (как ставятся скриптом)

- Скрипт ставит ручки только если `hardware.handles.count > 0`.
- Точка установки: по центру фасада по X, по `y = y2 - offset_from_top`, по Z = `z1` фасада.
- Для разных фасадов всегда используем их `placement` (иначе «ручки в одной точке»).

### 2.9. Направляющие (пока нет базы)

Если базы поставщика нет, тумба всё равно считается «готовой по геометрии».  
Дальше в БАЗИС:

- либо мастером «Установка ящиков» (направляющие + присадка),
- либо после появления каталога — заполнить `hardware.drawer_guides.furniture_encoded`.

## 3. Алгоритм работы ИМЕННО для тумб

Когда в ТЗ обнаружена тумба/тумбочка:

1. **Включить TUMBA_RULES.**
2. Выписать из ТЗ: W, D, H, T, Hleg, количество и типы секций (ящики/полки/двери), фурнитуру.\
3. Рассчитать корпус по §2.2–2.3 (корпус и зазоры по Z).
4. Если есть ящики — применить паттерн §2.4–2.5 для фасадов и коробов (своими числами).
5. Для открытых/дверных секций — §2.6.
6. Собрать `docs/<проект>_DIMENSIONS.md` с таблицами `placement` (по образцу `CABINET_DIMENSIONS.md`, но с новыми числами).
7. Собрать `examples/<проект>.json` по `schema/furniture.schema.json`:
   - `sections`, `panels`, `drawers`, `doors`, `hardware`, `carcass_calculation` с формулами ЭТОГО заказа.
8. `python main.py validate examples/<проект>.json`.
9. Скопировать в `basis_scripts/<проект>.json` и импортировать через `ImportFurnitureFromJSON.js`.
10. В БАЗИС проверить: зазоры, отсутствие пересечений, логика ящиков/полок/дверей.\
    При необходимости — мастер «Установка ящиков» / «Установка дверей» для фурнитуры.

## 4. Как агент должен ссылаться на базу для тумб

**Правило для себя (AI):**

> Если в ТЗ вижу, что изделие — тумба/тумбочка/близкий шкафчик, **обязательно** опираюсь на `TUMBA_RULES.md` + `INSTRUCT.md` и НЕ использую прямо координаты из `moderator_cabinet.json`. Беру только метод, формулы и структуру JSON.\
> Для других изделий (стойка, кашпо, стойка охраны и т.п.) TUMBA_RULES не включаю, опираюсь только на INSTRUCT и новое ТЗ.
