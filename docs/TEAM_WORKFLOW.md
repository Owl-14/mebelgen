# Командная работа без потери изменений

Этот регламент дополняет корневой [`AGENTS.md`](../AGENTS.md). Он одинаков для
людей, Codex и других агентов.

## 1. Базовая модель

```text
Linear/запрос
  → отдельная ветка и worktree
  → небольшой согласованный scope
  → локальные проверки
  → PR
  → CI + review
  → merge в master
  → отдельное решение о deploy
```

GitHub хранит код. Сервер хранит работающий артефакт и пользовательские данные.
Смешивать эти роли нельзя.

### Термины, чтобы не было скрытой полувыгрузки

| Команда | Где должен остановиться процесс |
|---|---|
| `сделай локально` | локальная ветка и локальный smoke |
| `закоммить` | локальный коммит в ветке задачи |
| `отправь в GitHub` / `сделай PR` | push + PR, без merge/deploy |
| `выгружай` / `публикуй` | CI + merge в `master` + deploy merge SHA + smoke |

Команду «выгружай» нельзя считать выполненной, пока GitHub `master`, merge SHA
и production `/version` не образуют одну цепочку.

## 2. Начало задачи

### Проверка контекста

```bash
git rev-parse --show-toplevel
git status --short --branch
git fetch --prune origin
git log -1 --oneline origin/master
```

Затем прочитать:

1. корневой `AGENTS.md`;
2. ближайший `AGENTS.md` в целевой папке;
3. профиль задачи из `docs/TASK_PLAYBOOKS.md`;
4. тикет/PR и связанные решения.

### Создание рабочей области

Предпочтительно отдельный worktree:

```bash
git worktree add ../mebelgen-<task> -b <branch> origin/master
```

Если worktree создаёт Codex Desktop, использовать выданную им рабочую папку и
не переключать её на ветку другого чата.

### Короткий контракт задачи

До кода зафиксировать:

- цель и проверяемый результат;
- затрагиваемые подсистемы;
- предполагаемые файлы;
- тесты;
- требуется ли изменение схемы/данных;
- требуется ли deploy (по умолчанию — нет).

## 3. Параллельная работа

### Правила владения

- Один исполнитель владеет своей веткой.
- Один горячий файл — один активный владелец, если изменения пересекаются.
- Общие схемы, goldens, материалы и инфраструктура меняются последовательно.
- Draft PR можно открыть рано, чтобы показать занятый scope.

### Если две задачи касаются одного файла

1. Разделить изменения по функциям/секциям, если это реально независимо.
2. Согласовать порядок merge.
3. Вторая ветка обновляется после merge первой.
4. Конфликт решается пониманием обеих сторон, а не выбором «ours/theirs»
   целиком.

Нельзя передавать незакоммиченный worktree другому чату как единственный
контекст. Передача должна содержать хотя бы diff и точное описание состояния.

## 4. Рабочий цикл

1. Воспроизвести исходное поведение или записать baseline.
2. Добавить/обновить тест, где это возможно.
3. Сделать минимальное изменение.
4. Запустить целевые тесты.
5. Проверить пользовательский сценарий.
6. Запустить полный гейт подсистемы.
7. Просмотреть diff и только потом готовить коммит/PR.

Для визуальных задач сохранять скриншоты «до/после» на одинаковом размере
viewport и на одних данных.

## 5. Коммиты

Рекомендуемый формат:

```text
AKD-123: краткий результат
```

Если тикета нет:

```text
docs: add team workflow guardrails
fix: keep Studio project selection after refresh
```

Не смешивать:

- массовое форматирование и функциональную правку;
- обновление зависимостей и новую функцию;
- production-конфиг и UI;
- несколько несвязанных тикетов.

## 6. PR и review

Шаблон описания:

```markdown
## Зачем
Какую проблему решаем.

## Что изменено
Подсистемы и ключевые решения.

## Как проверить
Команды и ручные шаги.

## Доказательства
Тесты, скриншоты, примеры payload/рендера.

## Риски и откат
Совместимость, данные, production-влияние.

## Deploy
Не требуется / требуется после merge с отдельным подтверждением.
```

Reviewer проверяет не только код, но и:

- не изменены ли данные/артефакты случайно;
- не появился ли второй источник правды;
- покрыта ли миграция старых ParamSpec;
- не расходятся ли Studio, viewer и `.cfrn/.b3d`;
- достаточно ли доказательств для визуального изменения.

## 7. Передача между чатами и людьми

Минимальный handoff:

```text
Задача:
Ветка:
База (SHA):
Что уже сделано:
Изменённые файлы:
Проверки и результат:
Что не проверено:
Открытые вопросы/риски:
Прод затрагивался: нет/да, что именно:
Следующий конкретный шаг:
```

Фразы «там почти готово» или «посмотри последние файлы» недостаточны.

## 8. Синхронизация с master

- Обновлять только собственную ветку.
- Перед PR убедиться, что ветка основана на актуальном `origin/master`.
- Не делать force-push после начала совместного review без предупреждения.
- После merge удалить ненужный worktree и ветку только когда результат точно
  сохранён в GitHub.

## 9. Разделение разработки и deploy

Merge не означает автоматический deploy.

Исключение — явная команда пользователя «выгружай/публикуй»: она заранее
разрешает полный release-цикл после успешных проверок. При красном CI, конфликте
или неготовом backup процесс останавливается до исправления, а не обходит гейт.

Deploy — отдельное действие с отдельным подтверждением. Перед ним фиксируются:

- SHA новой версии;
- SHA текущего `/version`;
- состояние backup;
- ответственный;
- smoke-сценарий;
- команда отката.

Ручные изменения в `/opt/bazis/basis` запрещены. Если prod требует срочного
hotfix, исправление сначала оформляется коммитом и только затем выкатывается
штатным скриптом.

### Release-чеклист

1. Рабочее дерево содержит только заявленный scope.
2. Полные гейты подсистемы зелёные.
3. Ветка отправлена в GitHub, PR описывает проверки, риски и откат.
4. CI зелёный; нерешённых конфликтов и review-блокеров нет.
5. PR смержен в `master`; зафиксирован merge SHA.
6. Перед deploy записаны текущий `/version` и состояние backup.
7. Штатный deploy получает merge SHA, а не имя рабочей ветки.
8. `/healthz`, `/version`, сервисы и пользовательский smoke проверены.
9. Локальный `origin/master`, GitHub `master` и `/version` совпадают.
10. Смерженная ветка и её worktree удалены после подтверждения результата.

## 10. Если что-то пошло не так

1. Прекратить новые изменения.
2. Сохранить логи, SHA и точное время.
3. Определить, затронуты ли пользовательские данные.
4. Если проблема после deploy — откатить известный SHA штатным путём.
5. Оформить исправление отдельной веткой и добавить регрессионный тест.
6. Обновить `AGENTS.md`/rules, если обнаружена новая повторяемая «грабля».
